# Progressive Web App

The application is installable as a PWA.

## What exists now, and what does not

| | Phase 1 — **done** | Phase 10 — not started |
| - | ------------------ | ---------------------- |
| Web app manifest | ✅ served at `/manifest.webmanifest` | — |
| Icons (192, 512, maskable) | ✅ project-owned PNGs in `public/icons` | — |
| Document metadata, theme colour, iOS tags | ✅ in `resources/views/partials/head.blade.php` | — |
| Service worker | ❌ **none** | to be written |
| Static asset caching | ❌ none | cache-first, Vite-hashed |
| Installability validation | partial | full |

**There is deliberately no service worker yet.** Registering an empty one would
make the application *look* installable and offline-capable while providing
neither, and a user who saw an install prompt would reasonably expect the app to
open without a connection. `tests/Feature/PwaManifestTest.php` asserts that no
service-worker registration appears in the markup and that no worker file is
served, so the absence is enforced rather than merely intended.

The manifest is generated by a controller rather than being a static file, so the
application name comes from configuration instead of being duplicated, `lang`
follows the current locale, and the whole thing is covered by tests — including a
check that every declared icon exists at the declared pixel size, since a manifest
that lies about its icons fails installability.

---

## Scope

This is a **deliberately limited** PWA. Internet availability at the business is
reliable, so there is no offline-first behaviour, no local database, and no
synchronisation layer.

| Built | Not built |
| ----- | --------- |
| Installable app with manifest and icons | Offline business data |
| Service worker caching the app shell and static assets | Local write queue |
| Network-first authenticated pages | Background sync |
| Clear failure when a write has no connection | Conflict resolution |

---

## Manifest

Served with the application shell and referenced from the document head:

- `name`, `short_name`
- `start_url`, `scope`
- `display: standalone`
- `theme_color`, `background_color`
- maskable icons at the sizes installability requires
- `lang` matching the user's locale where practical

---

## Service worker caching policy

The distinction that matters:

| Content | Strategy | Reason |
| ------- | -------- | ------ |
| Built CSS, JS, fonts, icons | cache-first, versioned by the Vite hash | Immutable per build |
| Application shell | cache-first with update-on-activate | Fast startup |
| Authenticated pages and data | **network-first / no-store** | Financial and milk data must never be served stale |
| POST, PUT, PATCH, DELETE | never cached, never queued | See below |

Caching an authenticated page risks showing one user's data to another on a
shared device, and stale milk or money figures are worse than no figures.

---

## Writes while offline

A write attempted without a connection **fails visibly**. The user sees a clear
connection error.

The application never displays a successful save that did not reach the server.
A queued-and-hopeful write would let someone believe a day's milk entry or a
payment was recorded when it was not, and the discrepancy would surface later as
missing money or missing litres.

---

## Cache invalidation

Vite emits content-hashed filenames, so a new build produces new asset URLs and
the old ones fall out of use. The service worker version is bumped with each
deploy so stale shells are discarded on activation.

---

## Verification

Checked in Phase 11, workflow J:

- The app installs on desktop and Android.
- The manifest and service worker are served and register without error.
- Static assets are cached and the shell starts quickly.
- Authenticated dynamic data is **not** cached for offline use.
- A write attempted offline shows a failure, not a false success.
